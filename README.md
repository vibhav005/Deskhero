# DeskHero 🦸

**Level up your health, one small quest at a time.**

DeskHero is a free, calm, gamified wellness app for people who spend long
hours sitting — software professionals, students, remote workers, and
freelancers. It turns tiny bursts of movement, hydration, posture care, eye
rest, and focused work into a friendly game of achievable quests.

This is **Phase 2: a real multi-user product** on Supabase (Postgres + Auth)
and Vercel, built entirely on free tiers — no AWS/GCP/Azure/Firebase, no paid
APIs, no monetization. (Phase 1 was a local-storage-only clickable prototype;
that code has been fully replaced by a real backend.)

> DeskHero provides general wellness guidance and is not medical advice. Stop
> exercising if you experience pain, dizziness, chest discomfort, or unusual
> shortness of breath.

---

## Product overview

- **Real auth** — email/password + magic link, email verification, password
  reset, session refresh via middleware.
- **Onboarding** — an 11-step, resumable flow persisted server-side (not lost
  on refresh or device change).
- **Home dashboard** — level & XP, daily score, streak, weekly rhythm, today's
  quests generated by a rule-based recommendation engine.
- **Adaptive daily quests** — 3–6 quests/day, scored and selected from the
  activity catalog based on goal, activity level, preferences, recent
  skip/completion history, and time-of-day; "Make Today Easier" and
  single-quest replace.
- **Guided workouts** and **Work Mode** (focus sessions with a movement-break
  prompt) — both route through the same server-validated completion path as
  regular quests.
- **Progress & achievements** — real aggregate stats, achievements with an
  immutable unlock timestamp and bronze/silver/gold tiers.
- **Reminders** — quiet hours, snooze, mute, daily cap, in-app + browser
  notifications (no push/background scheduling yet — see Limitations).
- **Community challenges** — create/join (public or invite-code), a
  leaderboard that never exposes emails, leave/rejoin preserving history,
  admin-disable, report.
- **Admin dashboard** — aggregate metrics, activity catalog CRUD, audited
  manual XP adjustments, feedback review.
- **Privacy controls** — opt-in analytics, full data export, progress reset,
  account deletion (password-reconfirmed).

### Design principles

Encouraging, beginner-friendly, calm, premium (not childish), and
non-judgemental. The app never shames a missed workout or a broken streak —
streak recovery is compassionate (a freeze, then a smaller "recovery" plan,
never a failure screen).

## Setup

Requires **Node.js 22+** (Supabase client packages require it) and a Supabase
project (free tier is sufficient).

### 1. Install

```bash
npm install
```

### 2. Create a Supabase project

Create a free project at [supabase.com](https://supabase.com), then collect:

- Project URL
- Anon (publishable) key
- Service-role (secret) key — **never expose this client-side**
- A [Personal Access Token](https://supabase.com/dashboard/account/tokens) (only needed for running migrations via the CLI, not at runtime)

### 3. Configure environment variables

Copy `.env.example` to `.env.local` and fill in:

```
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key>
SUPABASE_SERVICE_ROLE_KEY=<service role key>
SUPABASE_PROJECT_REF=<project-ref>
```

### 4. Run migrations and seed data

```bash
npx supabase login          # opens a browser to authorize the CLI
npx supabase link --project-ref <project-ref>
npx supabase db push        # applies every file in supabase/migrations/, in order
```

Then seed the content catalog (levels, activities, exercises, workouts,
achievements) by running `supabase/seed.sql` against the project — either via
the Supabase SQL Editor, or:

```bash
npx supabase db push --include-seed
```

(check `npx supabase db push --help` for your CLI version's exact seed flag;
the seed file is idempotent-safe to re-run via `on conflict do nothing` /
upsert patterns where it matters)

### 5. Generate types (after any schema change)

```bash
npx supabase gen types typescript --linked > src/types/database.ts
```

### 6. Run the app

```bash
npm run dev
```

Open <http://localhost:3000>. Sign up with a real email (or use Supabase's
Admin API to pre-confirm a test account if you're hitting the shared SMTP
provider's rate limit during heavy local testing — see Known Limitations).

## Testing

**Unit tests** (`npm test`, via Vitest) cover the pure logic that doesn't need
a database: the quest recommendation/selection engine (`src/lib/quest-engine.ts`
— scoring, category diversity, contraindicated-tag exclusion, the
guaranteed-very-easy-quest rule, and the single-quest replace path), the
leveling curve (`src/lib/logic.ts`), and timezone-aware date/hour computation
(`src/lib/tz.ts`, which `daily_plans.plan_date` and the reminder window logic
both depend on).

**Integration/E2E tests against a live Supabase project are not yet automated
in CI.** The original plan called for a second, dedicated free Supabase
project so tests never touch real user data — that's deferred. Until then,
every milestone's behavior (auth, RLS, the XP ledger, streaks, reminders,
challenges, admin functions) has been manually verified live against the real
project via Playwright + direct SQL checks during development, but there's no
automated regression suite for it yet. If you pick this up:

1. Create a second free Supabase project dedicated to CI.
2. Add its URL/keys as GitHub Actions secrets separate from the production ones.
3. Push migrations + seed to it in a CI step before running integration tests.
4. Playwright E2E should at minimum cover: signup → onboarding → dashboard,
   and generating + completing a daily quest.

## Data model

24 tables in `supabase/migrations/`. Key patterns, if you're extending this:

- **XP is never trusted from the client.** All XP moves through
  `award_xp()`, a `SECURITY DEFINER` Postgres function with a
  `UNIQUE(idempotency_key)` constraint doing the actual duplicate-prevention
  (not app-level check-then-insert). `xp_transactions` has `INSERT` revoked
  from `authenticated` entirely — the function is the only path in.
- **Internal-only Postgres functions must have `EXECUTE` explicitly revoked
  from `anon`/`authenticated`** (and from `PUBLIC` — both, since Supabase
  grants execute to specific roles *and* Postgres grants an implicit `PUBLIC`
  grant on function creation; revoking only one leaves it callable). See
  `supabase/migrations/20260727090001_harden_gamification_functions.sql` for
  why this matters: `award_xp` was directly callable via the PostgREST RPC
  endpoint before this was caught, letting any authenticated user grant
  themselves arbitrary XP.
- **Functions that accept a `p_user_id` parameter must assert it against
  `auth.uid()` internally**, not just trust the caller — a raw RPC call can
  supply any UUID it wants. `complete_activity_and_award_xp` and
  `complete_work_session_break` both do this.
- **Never expose emails.** Cross-user reads (challenge leaderboards/member
  lists) go through narrow `SECURITY DEFINER` functions that select only
  `profiles.display_name`, gated on the caller actually being a member —
  never a broad RLS policy on `profiles`, and never a join to `auth.users`.
- **RLS is the primary boundary**, with explicit `REVOKE` statements as
  defense-in-depth on tables where an omitted policy alone might not be
  obviously sufficient (e.g. `xp_transactions`, `audit_logs`,
  `user_achievements`).
- **Column-level grants** lock specific fields even when a table's RLS would
  otherwise allow a broader update — e.g. `profiles.current_xp` /
  `current_level` / `role` are excluded from the `authenticated` UPDATE
  grant entirely; `challenge_members.role` similarly, so a member can't
  rewrite their own row to say `owner`.

## Security notes

- A live XP-award vulnerability was found and fixed during development (see
  Data model above) — verified closed via direct RPC calls against the
  hosted project, both before and after the fix.
- A PL/pgSQL bug in `join_challenge_by_code` (relying on the ambient `FOUND`
  variable across multiple statements) silently dropped every new member's
  join while reporting success — found and fixed via live multi-user testing,
  not just code review.
- Every migration that introduces a function callable via RPC has been
  smoke-tested against the real hosted project (as both an authorized and an
  unauthorized caller) before being considered done.

## Known limitations

- **No dedicated CI/test Supabase project yet** — integration/E2E tests
  aren't automated (see Testing above).
- **Vercel deployment not yet configured** — env vars and a production
  deployment are a follow-up once a Vercel project exists.
- **Push/background reminders are deferred.** Reminders only fire while a
  tab is open (checked on load + every 15 minutes); there's no service
  worker or scheduled push yet.
- **Free-tier auto-pause**: Supabase free projects pause after 7 days with no
  traffic, which would silently stop `pg_cron` (streak processing). A
  scheduled GitHub Action pinging a health-check route is the cheap
  mitigation, not yet wired up.
- **Shared SMTP rate limits**: Supabase's default auth email provider is
  low-rate-limited. A burst of signups could delay verification emails.
  Configuring a free custom SMTP provider for auth email is a near-term
  priority before a real beta launch.
- **No challenge ownership transfer.** Deleting an account that owns a
  challenge deletes that challenge (and its shared history) for every
  member — there's no flow to hand ownership to another member first.
- **The Profile page's "Weekly streak freeze" control is a Phase 1 leftover**
  still wired to the old local-only client store, not the real
  `profiles.streak_freeze_available` column. Streak freeze consumption
  currently only happens automatically inside `process_daily_streaks()`;
  there's no manual "use my freeze now" action wired to the real backend.
- **`analytics_events` tracking covers 13 of the 16 planned event names.**
  `achievement_unlocked`, `streak_freeze_used`, and `streak_reset` happen
  entirely inside `SECURITY DEFINER` SQL functions rather than TypeScript
  Server Actions, so they'd need those functions extended to emit the event
  themselves — not done yet.
- **Admin promotion is DB-only.** There's no self-service or UI path to make
  a user an admin; it's a manual `update profiles set role = 'admin' ...`.
